# Dynamic MoE

Measurements for Dynamic MoE in 0.87.13. A mixture-of-experts model that does not fit in video
memory can leave whole layers of experts on the CPU, which is the classic expert offload, or it
can keep the most used experts of every layer on the card and compute the rest on the CPU, which
is what Dynamic MoE does. The tables compare the two at the same video memory, then show what the
prediction head, the Save RAM switch and a much larger model do.

## How this was measured

The engine the app ships, through `llama-server` with its own timings and flash attention on.
Each row is one server: a first prompt that is discarded, two prompts of about 2100 tokens, and
four answers of 256 tokens, two of prose and two of code, at a 32K context. Reading is the mean
of the two prompts and each generation figure the mean of its two answers, in tokens per second.

Unless a table says otherwise it is one run per row, and runs of the same row differ by about 3%,
so smaller gaps than that say nothing.

The rows for a card with less memory are not a smaller card. They are the same Radeon RX 6700 XT
with part of its memory held back, so the engine plans and runs inside 8 or 6 GB. A real card of
that size also has a slower GPU, which these rows do not show.

## Against expert offload at the same video memory

Qwen3.6-35B-A3B, UD-Q4_K_S, 20 GB, without its prediction head, on a Radeon RX 6700 XT with a
6-core Core i5 and 32 GB of RAM. The video memory is what the process really held.

| Video memory used | Mode | Reading | Prose | Code | RAM locked |
|---|---|---|---|---|---|
| 10.2 GiB | Dynamic MoE | **576** | **53.7** | **48.7** | 18.0 GiB |
| 10.3 GiB | Offload, 24 layers on the CPU | 365 | 29.8 | 29.8 | 10.8 GiB |
| 6.9 GiB | Dynamic MoE | **423** | **48.1** | **40.4** | 18.0 GiB |
| 6.9 GiB | Offload, 32 layers on the CPU | 85 | 25.6 | 25.6 | 14.1 GiB |
| 5.0 GiB | Dynamic MoE | **365** | **37.6** | **34.4** | 18.0 GiB |
| 5.0 GiB | Offload, 37 layers on the CPU | 81 | 23.4 | 23.4 | 16.3 GiB |

Dynamic MoE generates 1.5 to 1.9 times faster at every size, and with 5 GiB it still reads a
prompt as fast as offload does with 10. The price is RAM: it locks the whole bank of experts,
18 GiB here, where offload locks only the layers it keeps on the CPU.

Past about 30 layers on the CPU the expert prefetch stops paying for offload, and that is the 85
and 81 above. With the prefetch off it reads at 166 with 32 layers and 152 with 37, using 0.6 to
0.7 GiB less video memory, and generates the same.

## With the prediction head

The same model in the file that carries its MTP head, with the whole card.

| Head | Reading | Prose | Code |
|---|---|---|---|
| Off | 560 | 53.4 | 48.3 |
| On | 495 | **54.2** | **59.2** |

The head is worth 23% on code and nothing on prose, and costs 12% of reading speed because it
reads the prompt too. When a card has no room for it beside the model, the plan leaves it out and
starts without it instead of refusing.

## Save RAM

The switch keeps in RAM only the experts that are not in video memory, plus a margin of 8%. Same
model with its head on, in a session where the card had less free memory than above.

| | Whole bank in RAM | Save RAM |
|---|---|---|
| RAM locked | 18.5 GiB | **14.3 GiB** |
| Reading | 460 | 437 |
| Prose | 53.0 | 47.1 |
| Code | 55.5 | 46.0 |

It frees 4.2 GiB and costs 11% on prose and 17% on code. The first prompt after loading is the
slowest one, between 250 and 300 against 400, because the cache in RAM is smaller than the bank
and that prompt routes to nearly all of it. A wider margin buys little back: at 15% it locks
15.4 GiB, writes prose at the same speed and code 5% faster.

## A 177B model on one die

Qwen3.8-Flash-Next on one die of a Radeon Pro Vega II Duo, 32 GB of video memory, in a Mac Pro
with 512 GB of RAM. An 8K context, one prompt of prose and one of code, 256 tokens each. Its
prediction head is a separate file of 2.6 GiB, and the plan now counts it.

| File | Head | Prose | Code | RAM resident | RAM locked | Video memory |
|---|---|---|---|---|---|---|
| UD-Q4_K_XL, 111 GB | Off | 21.2 | 20.7 | 115.6 GiB | 72.9 GiB | 26.7 GiB |
| UD-Q4_K_XL, 111 GB | On | **25.4** | **31.4** | 115.8 GiB | 72.9 GiB | 23.3 GiB + head |
| UD-Q4_K_XL, Save RAM | On | 23.9 | 28.9 | 60.7 GiB | 59.4 GiB | 23.3 GiB + head |
| GSQ-RCO-Q2_0, 66 GB | Off | 19.2 | 18.8 | 54.2 GiB | 32.3 GiB | 28.5 GiB |
| GSQ-RCO-Q2_0, 66 GB | On | 24.1 | 28.0 | 54.5 GiB | 32.3 GiB | 25.1 GiB + head |

The head is worth 20% on prose and 52% on code with the larger file. The video memory with the
head on is read before the head loads, so its 2.6 GiB and its context come on top of the figure.

The smaller file uses less than half the RAM and is no faster, which these runs do not explain.
Its two rows come from a build four engine changes older than the rest of this page.
